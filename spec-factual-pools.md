# Spec: Factual Question Stem Pools and Distractor Sourcing (patch)

**Status:** Draft
**Date:** 2026-06-21
**Amends:** `20260621-pedagogical-principles-layer` §3 (R1) — already implemented. This spec does **not** edit that file; it explicitly **supersedes** R1.1's category scope and R1.2's distractor-generation mechanism as described below. Everything else in that spec (R2–R6) is untouched.
**Reason for patch:** post-implementation review found the original R1.2 assumption — that a single fixed template per category produces both an acceptable question stem and acceptable distractors with zero LLM involvement — does not hold once you leave a single narrow domain (the assumption was implicitly borrowed from Petrarca's history-only use case). Two distinct failure modes were identified: (1) a single fixed stem phrase becomes a recognizable, fatiguing pattern over a session; (2) distractors generated with no semantic grounding in the document's actual content risk being either trivially implausible or — worse — technically also correct.

---

## 1. What changes vs. the original R1

| | Original R1 (implemented) | This patch |
|---|---|---|
| Eligible categories for deterministic generation | dates, numbers-with-units, proper nouns, definitions, enumerations (all `factual`-classified) | **dates, numbers-with-units, proper nouns only.** Definitions and enumerations remain on the original LLM-generation path, unchanged (§4, non-goal). |
| Stem phrasing | one fixed template per category | a **pool of 8–12 phrasing variants per category**, rotating without repetition within a session — same mechanism already used for the 50-phrase header pool in RSVP pedagogy hardening (R1–R5). Reuse that selector if exposed; otherwise build the minimal equivalent (§7.2). |
| Distractor generation | generated by the same template, no grounding in document content | **sourced from sibling concepts of the same subtype already present in the document's `conceptInventory`** — never invented from nothing. |
| LLM involvement | zero, for all five categories | zero for the *stem*; **one batched LLM call per block** (not per concept) to validate/filter the sourced distractor candidates before they're shown. |
| Cost framing | "zero LLM calls for factual questions" | **no longer literally zero** for the three retained categories — one cheap batched call per block. Still a real saving vs. the pre-R1 baseline of one full LLM generation call per concept; just not free. This correction should be reflected wherever R1's cost savings were being tracked (`generation_method` tagging from the original spec stays relevant, but its values need a third state — see §7.4). |

`questionClass: 'factual' | 'conceptual'` classification (original R1.1's core mechanism) is **unchanged** — it still drives R2's comprehension gate regardless of which of the five factual subtypes a concept falls into. Only the *generation mechanism* for three of those five subtypes changes.

## 2. Why these three categories specifically, and not the other two

- **Dates/years**: temporally orderable, trivially comparable, and a document almost always contains multiple dates to source distractors from. Lowest risk.
- **Numbers with units**: comparable within the *same unit*, sourceable the same way — but only safe if distractor sourcing never mixes unit types (§3.2, a hard requirement, not a nice-to-have).
- **Proper nouns**: riskiest of the three retained categories because "what makes a wrong name plausible" depends on some notion of category (person vs. place vs. organization) that a document's inventory may or may not track explicitly (flagged as Open Question 7.1). Retained because the user judged the LLM validation pass sufficient to catch bad cases, not because it's mechanically as safe as dates.
- **Definitions and enumerations stay LLM-generated.** These require actual semantic judgment to phrase a plausible wrong definition or a plausible-but-wrong list — there's no equivalent "pull a sibling from the inventory" move that produces something coherent, the way there is for a date or a name. Not revisited in this patch; if this changes later, it's its own decision, not an extension silently absorbed here.

## 3. Distractor sourcing logic

**3.1.** New function `sourceDistractorCandidates(concept, conceptInventory, { category }) -> string[]`, called once per eligible concept:

- **`date`**: other date-type entries from the same document's inventory, preferring ones temporally distinct enough to be non-trivial (not "off by one year" unless that's genuinely the only pool available).
- **`number_with_unit`**: other numeric entries **matching the same unit type only**. Mixing a distance in km with a mass in kg as a "distractor" is not a hard question, it's a broken one — this matching is a correctness requirement, not a quality nicety.
- **`proper_noun`**: other named-entity entries, preferring same "kind" (person/place/organization) if the inventory tracks that distinction (Open Question 7.1); falls back to unfiltered proper-noun pool if it doesn't, which is weaker but acceptable for v1 since the validation pass (§5) is the real backstop here.

**3.2.** Minimum pool check: if fewer than 3 viable same-document, same-subtype candidates exist (common in short documents), **skip templated generation for that specific concept entirely** and fall back to full LLM generation for its options — per-concept granularity, consistent with how the rest of this codebase handles partial failure (never force a weak or repetitive question just to preserve the "zero LLM" framing for that one item).

## 4. Non-goals

- Extending deterministic generation to definitions or enumerations. Explicitly out of scope (§2).
- Reopening or modifying the `questionClass` classifier itself (R1.1 of the original spec) — unchanged.
- Modifying R2's comprehension gate — unaffected, it keys off `questionClass`, not the generation mechanism.
- Building a general-purpose "named entity kind" tagger if the inventory doesn't already have one — if Open Question 7.1 comes back negative, ship the weaker unfiltered fallback (§3.1) rather than building new extraction infrastructure as a side effect of this patch.

## 5. Stem phrasing pools

**5.1.** New or restructured `src/js/rsvp/factual-templates.js`: each of the three retained categories gets 8–12 phrasing variants, language-aware (`STUDY_LANG_OPTIONS`), e.g. for dates: "¿En qué año ocurrió X?", "¿Cuándo tuvo lugar X?", "X ocurrió en el año ___", etc. — varied enough that two consecutive factual questions in a session don't read as copy-pasted.

**5.2.** Rotation: no repeated phrasing for the same category within a single study session (track via session-scoped state, not persisted) — once the pool is exhausted, repetition is allowed (sessions are bounded; running out of 8–12 variants in one sitting is an edge case, not a design failure).

## 6. Validation pass (the actual safety net)

**6.1.** New function `validateDistractorBatch(items: [{ fact, candidateDistractors }]) -> [{ fact, approvedDistractors, rejected: [{ candidate, reason }] }]`, **one call per block**, covering every templated factual item generated for that block in a single request — not one call per concept. This is the entire cost-control point of this patch: the saving comes from batching the cheap validation, not from skipping validation.

**6.2.** Model: DeepSeek — consistent with the project convention that non-embedding LLM work uses DeepSeek (Gemini is reserved for embeddings).

**6.3.** The prompt instructs the model to reject a candidate distractor for exactly the three failure modes identified in review: **(a)** ambiguous relative to the fact, **(b)** technically also correct, **(c)** implausibly wrong (no real test of knowledge). Each rejection carries a one-line reason, logged for later spot-checking — same auditability standard as the rest of this codebase's automated decisions.

**6.4.** If validation drops a concept's approved distractor count below 3, that concept's options fall back to full LLM generation (same per-concept escalation pattern as §3.2) — never ship a 2-option or degraded MCQ to preserve the cost saving.

## 7. Implementation notes / open questions

**7.1.** Does `conceptInventory` track any sub-type/"kind" metadata for proper-noun entries (person/place/organization), or would same-kind distractor matching (§3.1) require new extraction work? Resolve before implementing the proper-noun branch — if absent, ship the weaker fallback rather than scope-creeping into building a new tagger (§4).

**7.2.** Is the 50-phrase header-pool rotation utility from RSVP pedagogy hardening (R1–R5) exposed as something this patch can call directly, or is it private to that module? If private, build the minimal equivalent rather than duplicating logic wholesale.

**7.3.** Does a `number_with_unit` inventory entry already carry a parsed/normalized unit field, or does unit-matching (§3.2) need to re-derive it from raw text at this stage? If re-derivation is needed, that's additional surface area worth flagging back rather than assuming it's free.

**7.4.** `generation_method` tagging (from the original spec's R1.5) needs a third value to stay accurate: `'template'` (stem only, no LLM at all — now only reachable if a future category is added with zero LLM involvement, currently none of the three retained categories qualify), `'template_validated'` (this patch's actual behavior — templated stem + sourced distractors + batched validation call), `'llm'` (full fallback, conceptual concepts or any factual concept that failed sourcing/validation minimums). Update the tagging logic accordingly so cost-savings measurement stays honest.

## 8. Risk-ordered implementation sequence

1. Stem pools + rotation (§5) — pure content/data, lowest risk, no dependency on the rest of this patch.
2. Distractor sourcing (§3) — moderate risk, the unit-type matching for numbers (§3.1, §3.2) is the trickiest correctness point; test it explicitly before moving on.
3. Validation pass (§6) — depends on §3 producing candidates to validate.
4. Wire the two fallback escalation points together (§3.2 pool-insufficient, §6.4 post-validation-insufficient) so a single concept can degrade gracefully through either path to full LLM generation without special-casing each one differently downstream.
