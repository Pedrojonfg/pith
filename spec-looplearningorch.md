# Spec: Autonomous Loop Engineering Orchestrator

**Spec folder:** `specs/20260717-loop-engineering/spec.md`
**Supersedes:** nothing (net-new capability). Builds on `overnight-debug-enrich` patterns but does not modify that branch/history.
**Author context:** designed conversationally with Claude; this document is the sole source of truth for implementation. Do not infer requirements from chat history not reflected here.

---

## 1. Purpose

Build an autonomous, unattended, multi-day loop that works through the 194-process audit inventory (`audit/process-inventory-20260717.md`), writes a test for each process, iterates a separate fix-agent against that test until it passes (or exhausts retry budget), and merges to `main` automatically with regression protection. Runs on a dedicated Oracle VPS inside a persistent `tmux` session, driven by a Python orchestrator that shells out to Cursor CLI (`agent -p`) headlessly. Must survive indefinitely without any human interaction: model exhaustion, transient hangs, VPS restarts, and multi-hour idle periods are all expected and must self-recover.

## 2. Non-goals

- Does **not** modularize/split `study.js`. That is an explicit follow-on project, deferred until this loop produces test coverage.
- Does **not** implement email notifications. ntfy.sh only.
- Does **not** attempt to resolve the 9 `unknown`-risk processes' *behavior* — only to determine reachability as a precursor step (see §8.4).
- Does **not** explode `llm-c-misc-enrichment` into its ~15 constituent contracts. Treated as one unit unless a future spec says otherwise.
- Does **not** require human review before merge. Auto-merge is the approved policy (see §9).
- Does **not** handle payment/credential entry, account creation, or any action outside the existing Cursor CLI + GitHub auth already configured on the VPS.

## 4. High-level architecture

```
orchestrator/
  main.py                 # entrypoint; loop driver
  inventory_parser.py      # parses process-inventory-20260717.md into structured records
  flow_grouper.py           # groups 194 processes into ~20 flow-group units per §5
  scheduler.py               # lock-based scheduler per §6
  agent_runner.py            # Cursor CLI invocation wrapper per §7
  verification.py            # 3-tier verification cascade per §8
  git_ops.py                  # branch/commit/merge/tag/push per §9
  notify.py                    # ntfy.sh wrapper per §10
  state.py                      # progress-file read/write, single source of truth per §11
  config.yaml                    # models, retry caps, lane caps, ntfy topic — see §12
progress/
  state.json                      # live state, machine-authoritative (see §11)
  run-log-<timestamp>.md           # append-only human-readable log per run
```

The orchestrator is a single long-running Python process. It does **not** spawn itself into background daemons; the `tmux` session provides persistence. On start, it always reads `progress/state.json` first and reconciles against `git log` on `main` before deciding what to do next (see §11.3) — it never trusts its own prior in-memory assumptions across a restart.

## 5. Flow-group derivation

### 5.1 Grouping rule

Reuse the inventory's own 20 `##`-level sections as the base grouping, **except** where a section's processes fan out across files with no real overlap (in which case sub-split), and **except** where processes in *different* sections share a hub file and must be sequenced relative to each other via the lock mechanism in §6, not by being merged into one group.

Concretely, `flow_grouper.py` must:
1. Parse each process row: `id`, `files_involved` (split on `,`), `depends_on` (free text — parse best-effort into a set of referenced process ids where the text names another `id` from the inventory; otherwise treat as an external dependency, not a scheduling edge), `static_risk_assessment`, `is_critical_path_for_demo`.
2. Start with one flow-group per inventory `##` section.
3. Within a flow-group, compute the set of `hub_files` touched = `files_involved ∩ {study.js, api.js, session-store.js}`.
4. Output a `flow_groups.json` manifest: `{group_id, section_name, process_ids[], hub_files[], non_hub_files[], priority_score}`.

`priority_score` = tuple sort key `(is_critical_path_for_demo == 'yes' ? 0 : 1, risk_rank)` where `risk_rank`: `likely-broken=0, unknown=1, likely-fragile=2, likely-fine=3`. Lower sorts first.

### 5.2 Special-case units

- `llm-c-misc-enrichment`: single unit, own flow-group, never split. Flag in manifest with `"collapsed": true`.
- The 9 `unknown`-risk processes (`boot-storage-migrate`, `pack-concept-editor`, `llm-c-guide-chat`, `llm-c-review-socratic`, `vault-extract-candidates`, `vault-curation-commit`, `adaptive-belief-persist`, plus any others matched by `static_risk_assessment == 'unknown'` at parse time — **do not hardcode this list, derive it from the parsed inventory**, this list is illustrative not authoritative): tag `"needs_recon": true` in the manifest. See §8.4.

## 6. Scheduling — lock-based concurrency

### 6.1 Locks

Three named locks: `study.js`, `api.js`, `session-store.js`. A flow-group requires a lock if `hub_files` contains that filename. A flow-group requiring zero hub files is `"free_lane": true`.

### 6.2 Scheduler loop (pseudocode, `scheduler.py`)

```
queue = sorted(flow_groups, key=priority_score)
active = {}   # lock_name -> flow_group currently holding it
free_lane_active = []  # up to FREE_LANE_CAP (config, default 2) concurrently running free-lane groups

loop:
  for group in queue (in priority order) if not group.done and not group.running:
    if group.free_lane:
      if len(free_lane_active) < FREE_LANE_CAP:
        launch(group); free_lane_active.append(group)
    else:
      required_locks = group.hub_files
      if all(lock not in active for lock in required_locks):
        # additionally: check depends_on edges against any group currently active anywhere
        if no active group is a depends_on target of this group, and vice versa:
          for lock in required_locks: active[lock] = group
          launch(group)
  wait for any running group to finish (blocking wait, not busy-poll — use subprocess completion callback)
  on finish: release locks held by that group; remove from free_lane_active if applicable; mark group state
```

Total concurrent agent processes at any time ≤ `1 (study.js) + 1 (api.js) + FREE_LANE_CAP (default 2)` = 4 by default. `FREE_LANE_CAP` is a config value, tunable without code changes.

### 6.3 Within a flow-group

Process-by-process, strictly sequential (one process id at a time, one commit per process id — see §9). The flow-group is the scheduling unit; the process is the commit unit. Do not parallelize within a group under any circumstance, even if two processes in the same group don't share a file — this preserves the "un proceso a la vez" principle and avoids compounding risk inside an already-locked file.

## 7. Per-process unit workflow

For each `process_id` within an active flow-group, in inventory order (or in `depends_on` topological order if intra-group dependencies exist):

### 7.1 Test-agent invocation

- Model: first entry of `config.test_agent_models` list (fallback chain, see §7.3).
- Prompt must include, verbatim: the inventory row for this `process_id`, the relevant entry from `bugs-found-20260717.md` if present, the relevant entry from `enrichment-log-20260717.md` if present, the process's `static_risk_assessment` (this determines whether the agent should write a deterministic exact-match fixture test or a property-based/structural test per §8), and an explicit instruction that it may **only** create/modify test files (path convention: `test/loop-engineering/<process_id>.test.mjs` or equivalent per existing test runner conventions — verify actual test runner and existing test file conventions via repo inspection before assuming `.mjs`/`node --test` layout), and must **not** modify any source file.
- Command shape: `agent -p --force --model <model> "<prompt>"` run with cwd set to repo root on a dedicated branch (see §9.1), with a hard timeout (`config.agent_timeout_seconds`, default 600) via `subprocess.run(..., timeout=...)`. On `TimeoutExpired`, kill the process tree (not just the parent PID — Cursor CLI may spawn children) and treat as one failed attempt against the retry budget in §7.3.
- After the test-agent's file changes are written, `git diff --name-only` must be checked against an allowlist restricted to test-file paths. If the test-agent touched anything outside that allowlist, discard the changes (`git checkout -- .`) and treat as a failed attempt — this is the enforcement mechanism for "fix-agent cannot edit the test," applied at the source: the test-agent itself is boxed in.
- Commit: `test(<process_id>): add fixture/verification` on the process branch.

### 7.2 Fix-agent invocation

- Model: first entry of `config.fix_agent_models` list.
- Prompt: the same inventory row context, the test file just written (full contents), and explicit instruction to make the test pass by modifying source only, never the test file. Enforce via the same allowlist-diff mechanism as §7.1, inverted (fix-agent's diff must **exclude** the test file path; if it touches the test file, discard and count as failed attempt).
- Runs the actual test command after each fix-agent invocation to check pass/fail (test command derived from repo's existing test runner — verify via `package.json` scripts or existing CI config before assuming `node --test`).
- Retry loop: up to `config.max_fix_attempts` (default 6, configurable) attempts. Each attempt is a fresh `agent -p` invocation with the accumulated conversation state cleared (each attempt gets the original prompt + a summary of the previous attempt's failure output appended — do not let context grow unbounded across attempts; truncate prior failure output to last 200 lines).
- If test passes: proceed to §8 (verification cascade) before considering the process complete — passing the fix-agent's own test is necessary but not sufficient; §8 tier 2/3 checks apply where relevant.
- If all attempts exhausted without pass: mark process `blocked` in state, commit whatever partial work exists on the process branch under a clearly marked WIP commit (`wip(<process_id>): blocked after N attempts, see progress/state.json`), do **not** merge to `main`, notify via ntfy (§10), and move to the next process in the flow-group.

### 7.3 Model fallback

`config.test_agent_models` and `config.fix_agent_models` are ordered lists, e.g.:
```yaml
test_agent_models: ["composer-2.5", "claude-sonnet-4-6", "gpt-5-mini"]
fix_agent_models:  ["grok-4.5", "claude-opus-4-8", "composer-2.5"]
```
On any invocation failure matching a rate-limit/credit-exhaustion signature (match against known Cursor CLI error strings — **verify exact error text by triggering a real rate-limit during implementation testing rather than guessing**, this is a testable precondition not a documentation lookup), advance to the next model in the list for that specific attempt only (does not change the list order for future units). If the entire list is exhausted for a role, the orchestrator enters a backoff-wait state (`config.exhaustion_backoff_seconds`, default 1800, exponential up to a cap of 4 hours), retries the first model in the list after the wait, and logs + notifies (once per exhaustion event, not per retry, to avoid ntfy spam) that it is waiting on model availability. It never blocks indefinitely without periodic retry, and never requires manual config edits to resume.

## 8. Verification cascade

Applied after a fix-agent's own test passes, before merge is authorized. Tier applied depends on the process's nature, determined by `static_risk_assessment` category **and** whether `files_involved` includes an LLM-contract file (`api.js`, `llm.js`, or any `llm-c-*` id prefix) — deterministic pipeline/persistence processes get Tier 1 only; LLM-generative processes get Tier 1 + Tier 2, escalating to Tier 3 only for the small set of genuinely subjective processes (Socratic tutor quality, review generated batch, recall tutor — enumerate exactly which `process_id`s require Tier 3 in `config.tier3_process_ids`, do not infer this list algorithmically from risk level alone).

- **Tier 1 — Structural (no LLM call).** Schema/shape validation: correct field presence, no duplicate ids, no orphan graph nodes, correct array lengths where deterministic, no thrown exceptions on the fixture set. Implemented as plain assertions in the test file itself (this is what the test-agent writes in §7.1 for deterministic processes).
- **Tier 2 — Source-grounding via embeddings (no generative LLM judgment).** For generated concepts/questions/items: embed the generated text and the source document (or relevant chunk) using the existing `gemini-embedding-001` pipeline already in the codebase (`vault/embeddings.js` or equivalent — reuse, do not reimplement), and assert cosine similarity exceeds a threshold (`config.grounding_similarity_threshold`, default 0.75 — **flag as an unvalidated placeholder per project convention**, to be calibrated post-launch like all other thresholds in this codebase). Failing this tier does not immediately fail the process; it triggers Tier 3 only if that process is in `tier3_process_ids`, otherwise it fails the unit and returns to the fix-agent retry loop with the grounding failure appended to context.
- **Tier 3 — LLM judge (DeepSeek, last resort, fixed rubric only).** Structured-output call to DeepSeek with a fixed JSON schema output (never free-form "is this good?"). Rubric fields are process-specific and must be defined per `tier3_process_ids` entry in `config.yaml` (e.g., for `llm-c-socratic-tutor`: `{grounded: bool, addresses_question: bool, no_hallucinated_facts: bool}`). All fields must be `true` for pass. This uses DeepSeek explicitly (not Mistral) per Pedro's decision — this is development-time tooling against fixture documents, not production user-data processing, so the GDPR/Mistral-only constraint does not apply here.

## 9. Git workflow

### 9.1 Branching

One branch per **process**, not per flow-group: `loop-eng/<process_id>`, created from current `main` tip at the start of §7.1. Branch is deleted after successful merge (local and remote). If blocked (§7.2 exhaustion), branch is **kept** (not deleted) with the WIP commit, for later human inspection — this is the one place partial work is visibly retained rather than discarded.

### 9.2 Checkpoint + regression gate (pre-merge, mandatory, applies to every successful process)

1. Before merge: `git tag checkpoint-before-<process_id> main`.
2. Run the **full accumulated test suite** of all previously-merged loop-engineering tests (not just this process's new test) against the fix-agent's branch merged locally (test in a throwaway merge, not on `main` directly — e.g. `git worktree` or a temp merge commit that gets discarded if it fails).
3. If full suite passes: fast-forward or merge-commit `main` to include this branch, push to `origin main`, delete the process branch (local + remote).
4. If full suite fails: do **not** merge. Reset any temp state, mark process `blocked` with reason `regression`, keep the branch, notify via ntfy, move to next process. This is distinct from a fix-agent retry exhaustion — it means the fix worked for its own test but broke something else; do not silently retry into this without a human eventually looking, since the fix-agent's next attempt would be reasoning from a broken premise.
5. On successful merge, push immediately (`git push origin main`) — do not batch pushes. This is the durability guarantee against VPS loss.

### 9.3 Commit granularity

One commit per process for the fix (`fix(<process_id>): <one-line description>`), one commit per process for the test (`test(<process_id>): add verification`), matching the debug-enrich convention of one commit per unit of work. Never squash across processes.

## 10. Notifications (ntfy.sh)

Fire-and-forget `curl` POST to `https://ntfy.sh/<topic>` (topic from `config.yaml`, generated once at setup per §3). Events that trigger a notification:

- Orchestrator start / resume (with a summary: N processes remaining, current flow-group).
- A flow-group completes fully (all its processes merged or blocked).
- A process is marked `blocked` (regression or exhausted attempts) — include `process_id` and reason.
- Model exhaustion entering backoff-wait (once per exhaustion event, not per retry attempt).
- Full run completion (all 194 processes reach a terminal state).
- Any unhandled exception in the orchestrator itself that would otherwise cause a silent stop — this is the one case where the orchestrator should notify **before** attempting any auto-recovery, since an unknown failure mode is exactly the case Pedro needs visibility into fastest.

Do not notify per individual process success — that would be dozens of notifications a day and defeats the purpose. Batch routine progress into the flow-group-complete event.

## 11. State management (`progress/state.json`)

### 11.1 Schema

```json
{
  "run_started_at": "ISO8601",
  "last_updated_at": "ISO8601",
  "flow_groups": {
    "<group_id>": {
      "status": "pending | active | done",
      "processes": {
        "<process_id>": {
          "status": "pending | test_written | fixing | verified | merged | blocked",
          "attempts": 0,
          "block_reason": null,
          "branch": "loop-eng/<process_id> | null",
          "merged_commit_sha": null
        }
      }
    }
  },
  "active_locks": ["study.js"],
  "model_exhaustion": { "test_agent": null, "fix_agent": null }
}
```

### 11.2 Authoritativeness

`state.json` is authoritative for **scheduling** (what to run next), but `main`'s git log is authoritative for **what is actually merged**. On every startup (including resume after any interruption), the orchestrator must reconcile: for any process marked `merged` in state, verify `merged_commit_sha` actually exists in `git log main`; if not, revert its status to `pending` and log a warning (this handles the edge case of a crash between local merge and remote push). For any process marked `verified` or `fixing` with no corresponding merge in `main`, treat as `pending` and restart from §7.1 for that process — never resume mid-attempt, always restart a process cleanly rather than trying to recover partial agent state, since Cursor CLI sessions are not reliably resumable mid-conversation.

### 11.3 Startup reconciliation sequence

1. Read `state.json`. If absent, initialize from `flow_groups.json` (all `pending`).
2. `git fetch origin main && git log main` to get merged process ids (parse from commit message convention in §9.3 — commit messages are the ground truth, not free-text inference).
3. Reconcile per §11.2.
4. Resume scheduler loop from reconciled state.

## 14. Non-goals reiterated for emphasis

Do not attempt to auto-fix a `blocked` process by relaxing its test. Do not let the fix-agent see or infer the verification-cascade thresholds and optimize against them beyond making the actual behavior correct — thresholds are for the orchestrator's gating logic only and must not appear in fix-agent prompts. Do not merge `llm-c-misc-enrichment` sub-fixes individually; it is one process for scheduling and commit purposes per §5.2 until a future spec says otherwise.
